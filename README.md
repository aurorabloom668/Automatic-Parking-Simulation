A Prius parking simulation built with **ROS 2 Humble, Gazebo Classic 11, and RViz2**, supporting parallel and perpendicular parking. Two parking workflows are retained:

| Mode | Launch file | Workflow |
| --- | --- | --- |
| Preplanned route | `planned_park.launch.py` | Automatically follows a fixed sequence: reverse perpendicular parking → exit and drive along the aisle → parallel parking |
| Online Hybrid A* | `auto_park.launch.py` | Manually approach → select a free slot → meet entry conditions → start → plan and track locally |

**Online parking is not long-distance navigation. Drive manually near the selected slot before starting automatic parking. Moving from one parked slot to another also requires a manual, safe exit first.**

## Environment and installation

The current development environment is Ubuntu 22.04, ROS 2 Humble, Gazebo **Classic 11**, Python 3, and Qt5. This project does not use Gazebo Sim / Ignition Gazebo.

Install ROS 2 Humble first. After obtaining the project, run the following from the repository root containing `src/`. If rosdep has not been initialized, run `sudo rosdep init` once after installing `python3-rosdep` and before `rosdep update`.

```bash
sudo apt update
sudo apt install python3-colcon-common-extensions python3-rosdep \
  ros-humble-gazebo-ros-pkgs ros-humble-rviz2 \
  libgazebo-dev libignition-math6-dev qtbase5-dev

source /opt/ros/humble/setup.bash
rosdep update
rosdep install --from-paths src --ignore-src --rosdistro humble -r -y
colcon build --symlink-install --cmake-args -DBUILD_TESTING=OFF
source install/setup.bash
```

Source both ROS and the workspace in every new terminal used for launching or debugging.

### External Gazebo models

The default [park.world](src/car_demo/car_demo/worlds/park.world) needs five external model directories **not bundled with this repository**: `suv`, `hatchback`, `hatchback_blue`, `hatchback_red`, and `house_1`. These scene assets are available in the upstream [OSRF Gazebo model database](https://github.com/osrf/gazebo_models).

Prepare them under `~/.gazebo/models/`, or add their parent directory to `GAZEBO_MODEL_PATH`, before launching. Keep the complete model directories, including configuration, SDF, meshes, materials, and textures. The base `hatchback` supplies resources shared by the blue and red variants. The launch file disables the online model database, so missing models **will not be downloaded automatically**. Prius meshes, parking-slot assets, and construction cones are included in the project.

## Mode 1: preplanned parking demonstration

```bash
ros2 launch auto_parking planned_park.launch.py
```

This starts Gazebo, the vehicle, RViz, and the fixed-route controller. The mission runs automatically after the vehicle is ready; no slot selection is required. Its straight and arc segments are designed for the default scene and spawn pose, rather than generated by Hybrid A*.

See [parking.yaml](src/auto_parking/config/parking.yaml) for configuration and [mission.py](src/auto_parking/auto_parking/mission.py) for the route. This mode currently sets `safety_enabled: false`; use it as a fixed-scene demonstration, not as a dynamic obstacle-avoidance system.

## Mode 2: manual approach + Hybrid A* parking

```bash
ros2 launch auto_parking auto_park.launch.py
```

The unified launch starts the simulation and a native RViz `ParkingPanel` docked on the left. Its controls currently use Chinese labels:

1. Stay in **手动驾驶** (Manual driving) and drive using the panel buttons or keyboard.
2. Use RViz **Publish Point** to select a green, free parking slot. Red means occupied; yellow means selected.
3. Selection only displays the target footprint and nearby activation boundary. It does not plan or take control. Manually approach if the slot is far away.
4. Stop near the slot and wait for `READY_TO_PARK` and the enabled **开始自动泊车** (Start automatic parking) button.
5. Click that button. The system switches to automatic mode and plans/tracks the maneuver. Do not switch the mode selector in advance to approach manually.
6. Check `COMPLETE` and the final parking metrics. Switch back to **手动驾驶** to resume manual driving.

Default entry conditions include a shortest distance of **12 m or less from the rear-axle reference point to the slot rectangle**, absolute speed at most **0.15 m/s**, an unoccupied target, the vehicle not fully parked inside another slot, and sufficient obstacle clearance at the current and target footprints. There is **no initial heading restriction**. Readiness does not guarantee a feasible route; full-path collision and kinematic checks happen when planning starts.

The boundary is a nearby activation region, not a global navigation range, a fixed staging pose, or an alignment corridor. The current radius is 12 m, not the approximately 6 m proposed in earlier design notes.

Light-blue path segments indicate forward motion, dark-blue segments reverse motion, and yellow points gear changes. The planner allows forward/reverse entry and corrective maneuvers; **it does not enforce reverse-only entry**. The direction depends on feasibility and cost.

**取消** (Cancel), **急停** (Emergency stop), or failure stops the vehicle. Switch back to Manual driving before driving again. To move to another slot after parking, exit manually and approach the new slot first; no dedicated automatic exit strategy is implemented.

### Manual panel controls

Give the panel keyboard focus. Hold a driving key/button to drive; releasing it or losing panel focus applies the brake.

| Keys | Action |
| --- | --- |
| `W` / `Q` / `E` | Forward / forward-left / forward-right |
| `X` / `Z` / `C` | Reverse / reverse-left / reverse-right |
| `A` / `D` | Steer left / right without throttle |
| `S` / `Space` | Brake and select neutral |
| `R` / `F` | Increase / decrease throttle magnitude |
| `T` / `G` | Increase / decrease steering magnitude |

Both parking launches start a complete simulation; **run them separately**. Online mode already includes manual control. Do not also run the standalone terminal keyboard node, which publishes directly to `/prius/control` by default and would bypass arbitration.

## Planning, configuration, and interfaces

Online mode uses local Hybrid A* with Reeds–Shepp heuristics/analytic connections and an obstacle-aware heuristic. Costs account for path length, forward/reverse motion, gear changes, steering, and clearance. Tracking uses curvature feedforward plus lateral/heading feedback, with final-pose corrections and stop-before-replanning when the remaining path becomes obstructed.

Main settings are in [hybrid.yaml](src/auto_parking/config/hybrid.yaml):

| Parameter | Default | Meaning |
| --- | --- | --- |
| `activation_radius` | 12.0 m | Entry distance from rear axle to slot rectangle |
| `entry_speed` | 0.15 m/s | Maximum absolute speed to start |
| `position_tolerance` | 0.10 m | Separate longitudinal and lateral completion limits |
| `yaw_tolerance` | 0.05236 rad (3°) | Completion heading-error limit |
| `stop_speed` | 0.05 m/s | Completion absolute-speed limit |
| `minimum_clearance` | 0.10 m | Minimum vehicle-to-obstacle clearance |
| `max_adjustments` | 5 | Shared budget for final corrections and obstacle-triggered replans |
| `speed_forward` / `speed_reverse` | 0.70 / 0.45 m/s | Normal forward / reverse target speed |
| `speed_fine` | 0.20 m/s | Fine-adjustment target speed |

Completion also requires the full vehicle body inside the slot. Rebuild and source the workspace after changing configuration or source files.

Important interfaces are `/clicked_point` (slot selection), `/parking/command` (`manual`, `auto`, `start`, `cancel`, `estop`), `/parking/status` (state, reasons, and metrics), and `/parking/manual_control` / `/parking/auto_control` (control inputs). In online mode, `control_mux` alone publishes the resulting `/prius/control`. Localization comes from `/prius/ground_truth`. Despite its name, `/prius/center_laser/scan` carries `sensor_msgs/msg/PointCloud2`.

Use `ros2 topic echo /parking/status` for diagnosis. If the panel is missing, verify the build and sourced workspace, or add `auto_parking/ParkingPanel` through `Panels → Add New Panel` in RViz.

## Tests and limitations

After the base build, enable and run the parking package tests:

```bash
colcon build --packages-select auto_parking --symlink-install --cmake-args -DBUILD_TESTING=ON
source install/setup.bash
colcon test --packages-select auto_parking --event-handlers console_direct+
colcon test-result --test-result-base build/auto_parking --verbose
```

Tests cover geometry/collision checks, local planning, offline closed-loop tracking, perception, supervision, arbitration, ROS topic flow, and panel loading. They do not replace end-to-end parking validation with Gazebo vehicle dynamics.

The system targets the supplied parking lot. Slot candidates and static obstacle priors are defined in [spots.py](src/auto_parking/auto_parking/spots.py) and [collision.py](src/auto_parking/auto_parking/collision.py), with lidar supplementing occupancy and obstacle information. This is not general-purpose parking-slot detection. Update those priors when changing the scene, and update the fixed mission for preplanned mode. Localization uses simulation ground truth; this project is not ready for direct deployment on a real vehicle.

```text
car_parking/
├── src/
│   ├── auto_parking/           # Parking workflows, arbitration, RViz panel, config, tests
│   └── car_demo/
│       ├── car_demo/           # Gazebo launches, parking lot, vehicle plugin, keyboard control
│       ├── prius_description/  # Prius URDF, meshes, and textures
│       └── prius_msgs/         # Vehicle control messages
├── README.md                   # English
├── README_CN.md                # Chinese
└── .gitignore
```

[.gitignore](.gitignore) excludes build/install/log output, caches, local tool settings, and common recording files. Required `.obj` vehicle meshes and textures remain part of the source tree.

In the current working directory, `src/car_demo` is still a nested Git repository with local modifications. **Before publishing, decide whether to include its complete source or commit the changes and reference them as a proper submodule.** An outer `git add` may record only a gitlink, leaving future clones without the modified source; the root `.gitignore` does not resolve this.
